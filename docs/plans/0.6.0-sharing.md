# 0.6.0 — sharing, scopes, and file requests

Status: **proposed** · Date: 2026-11-20
Builds on: [ui.md](ui.md), [future.md](future.md), RFC 0003 (sharing),
RFC 0007 (E2EE), RFC 0010 (DAV/E2EE boundary)

This is a preparation document, not implementation. It covers the three
workstreams selected for the next product cycle:

1. **Shared page** — make existing shares manageable from one place.
2. **Scoped app passwords** — stop issuing full-account device tokens.
3. **Upload-only links** — the missing “file request” half of sharing.

## 1. Sequencing

| Track | Content | Migrations | Suggested release |
| --- | --- | --- | --- |
| **A** | Shared page, link expiry/copy/revoke | None | **0.6.0** |
| **B** | Scoped/expiring app passwords | One | **0.6.0** |
| **C** | Upload-only links / file requests | One or two | **0.7.0** |

Recommended split:

- **0.6.0 = A + B.** The Shared page is UI over existing APIs; scoped tokens
  are a contained security improvement. Both can ship without a new public
  upload surface.
- **0.7.0 = C.** Upload-only links need abuse controls, new public endpoints,
  and a security review. Do not bolt them onto 0.6.0 late.

If a single release is required, keep the same order and treat C as the gate:
do not tag until the upload abuse tests pass.

## 2. Track A — Shared page

### Goal

One page that answers: **what have I shared, with whom, until when, and how do
I revoke it?** Plus a received view that shows owner, permission, and lock
state even before the vault is unlocked.

### Existing APIs

| Need | API |
| --- | --- |
| Received shares | `GET /api/shares/received` |
| Created shares | `GET /api/shares/owned` |
| Shares for one path | `GET /api/shares?path=` |
| Update permission/expiry/password | `PATCH /api/shares/{id}` |
| Revoke | `DELETE /api/shares/{id}` |
| Create | `POST /api/shares` |

`/api/shares/owned` already returns `kind`, `recipient`, `path`, `name`,
`permission`, `url`, `expires_at`, `created_at`, and `missing`.
`/api/shares/received` returns `share_id`, `owner`, `name`, `mount`, `kind`,
`permission`, `size`, `modified_at`, `encrypted`, and `wrapped_name`.

### UI

Add `Tab::Shared` and route `#/shared`. Sidebar order: Files, **Shared**,
Trash, separator, Settings, Admin.

Three sections or tabs:

- **Received** — owner, permission, path, size, modified, lock state. Decode
  names when the keyring is unlocked; otherwise show “Encrypted share”.
  Open navigates to the mount.
- **Created** — recipient (`user`, `group`, or “Public link”), path,
  permission, created, expiry, and a `missing` badge. Actions: revoke,
  copy link, adjust user/group permission, set a new link password.
- **Links** — filter `kind == "link"`; show URL, created/expiry, copy,
  revoke. Passwords are write-only after creation; offer “Set new password”.

### Encrypted public links

The server returns only `/s/<token>`; the useful link for an encrypted file
also carries `#k=<key>&l=<lengths>&n=<name>`. The fragment never reaches the
server.

- While the vault is unlocked, rebuild the fragment from the wrapped file key
  and manifest when the user copies the link.
- Do not persist link keys by default. If an explicit “remember this link key”
  option is added, scope it to that share and clear it on sign-out.
- If the vault is locked, show **Unlock encryption to copy the full link**
  instead of copying a broken URL.
- Encrypted folder links: only support copy when the client can rebuild the
  required name/member keys. Otherwise say so explicitly.

### Expiry and permissions

- Link expiry presets: Never, 1 day, 7 days, 30 days, custom. Map to
  `expires_in_secs` (`0` = never) on create and `PATCH` on edit.
- User/group permission: read/write only.
- Link permission: read-only for view links; write is reserved for Track C.

### Tests

- Create user/group/link shares through the API; see all three in Shared.
- Revoke from the page; the share disappears.
- Edit expiry and permission; reload and confirm.
- Encrypted file link: copy while unlocked produces a working fragment; copy
  while locked shows the unlock action.
- Axe on the Shared page.
- Mobile layout: three tabs fit, rows wrap, bulk actions not required here.

### Acceptance

A user can manage every share they created, and see every share they received,
without opening each file. No server-side fragment storage is introduced.

## 3. Track B — scoped app passwords

### Goal

App passwords currently grant full account access. Add least-privilege scopes
and optional expiry so a calendar client cannot delete files, and a sync
client cannot manage users or share links.

### Data model

Add one migration after `0031_mfa_onboarding.sql`:

```sql
ALTER TABLE app_passwords ADD COLUMN scopes TEXT NOT NULL DEFAULT '*';
ALTER TABLE app_passwords ADD COLUMN expires_at INTEGER;
```

`scopes` is a comma-separated list or JSON array. Keep `*` as full access for
every existing row and for backward compatibility. Add `expires_at` as Unix
milliseconds; `NULL` means no expiry.

Optional follow-up: `last_used_ip` is not needed; `last_used_at` already
exists.

### Scope model

Start with coarse, protocol-oriented scopes:

| Scope | Allows |
| --- | --- |
| `*` | Everything the account can do (existing behavior) |
| `files:read` | WebDAV/JSON file reads, listings, search, previews, trash/version reads |
| `files:write` | File writes, deletes, moves, mkdir, trash/version restore; implies read |
| `caldav:read` | CalDAV discovery, PROPFIND, REPORT, GET |
| `caldav:write` | Calendar object/collection writes; implies read |
| `carddav:read` | CardDAV discovery, PROPFIND, REPORT, GET |
| `carddav:write` | Address-book writes; implies read |
| `sync` | Delta-sync transport, chunks/manifests, keyring/identity, MLS sync |

Default for new UI-created tokens: **Files read/write + Sync** if the user
chooses “Sync client”; **Calendars + Contacts** for a DAV client; **Full
access** remains an explicit choice with a warning.

### Enforcement

Do not add fields to `CurrentUser`. Attach a separate request extension:

```rust
pub struct AppPasswordAuth {
    pub id: i64,
    pub scopes: ScopeSet,
    pub expires_at: Option<i64>,
}
```

Authentication flow:

1. `authenticate_basic` checks app passwords before the account password.
2. On a match, load scopes/expiry, reject expired tokens, touch
   `last_used_at`, and return `AuthProof::AppPassword(...)`.
3. `require_auth` inserts `AppPasswordAuth` into request extensions.
4. A single `authorize_scope` check runs after the password/MFA gates and
   before the handler. **Deny by default** for any path not in the matrix.
5. Session and account-password requests carry no `AppPasswordAuth` and keep
   full access.

Path/method matrix (prefixes are checked longest-first):

| Path | Read methods | Write methods |
| --- | --- | --- |
| `/dav/calendars` | `caldav:read` | `caldav:write` |
| `/dav/addressbooks` | `carddav:read` | `carddav:write` |
| `/dav/principals`, `/dav/` discovery | any of `files:*`, `caldav:*`, `carddav:*` | — |
| `/dav` file tree | `files:read` | `files:write` |
| `/api/browse`, `/api/search`, `/api/preview`, `/api/files/info` | `files:read` | — |
| `/api/files/move`, `/api/files/encrypt` | — | `files:write` |
| `/api/chunks`, `/api/files`, `/api/sync`, `/api/trash`, `/api/versions` | `sync` or `files:read` | `sync` or `files:write` |
| `/api/e2ee/keyring`, `/identity`, `/enrollments`, `/devices` GET | `sync` | — |
| `/api/mls/*` | `sync` | `sync` |
| `/api/me`, `/api/users`, `/api/invites`, `/api/audit`, `/api/me/app-passwords`, `/api/shares` | `*` only | `*` only |
| `/metrics` | separate metrics token | — |

Write methods are `PUT`, `POST`, `PATCH`, `DELETE`, `MKCOL`, `MKCALENDAR`,
`MOVE`, `COPY`, `PROPPATCH`, `LOCK`, `UNLOCK`. Safe methods are `GET`, `HEAD`,
`OPTIONS`, `PROPFIND`, `REPORT`. Unknown methods require `*`.

Return `403` with a small JSON error for API paths; for DAV, return `403`
without a Basic challenge (re-challenging would loop). Never fall back to a
cookie session when Basic app-password scope fails.

### API and UI

Extend `POST /api/me/app-passwords`:

```json
{
  "name": "Laptop sync",
  "scopes": ["files:read", "files:write", "sync"],
  "expires_in_secs": 0
}
```

`GET` returns `scopes` and `expires_at`; `PATCH` can rename, change scopes, or
change expiry; `DELETE` stays. Validation rejects unknown scopes and
`expires_in_secs < 0`.

In **Settings → Passkeys → App passwords**:

- Preset selector: Full access, Sync client, Files read-only, Files read/write,
  Calendars & contacts, Custom.
- Expiry: never / 30 days / 90 days / 1 year.
- List shows scope badges, created, last used, expiry; revoke stays.
- “Full access” shows a warning that the token can manage the account.

### Migration and compatibility

- Existing rows default to `*`; no forced rotation.
- Existing clients continue to work.
- Document that old tokens are full-access and should be reissued if the user
  wants least privilege.
- Consider a later “expire all app passwords older than…” admin action; not in
  this track.

### Tests

- Rust: each scope allowed/denied against representative API and DAV routes.
- Scope write implies read; `*` still works.
- Expired token returns 401; revoked token returns 401.
- Scope failure does not fall back to cookie auth.
- UI: create each preset, see badges, revoke.
- Backward compatibility: existing app password row with default `*`.
- `cargo vet`/supply chain unaffected; no new crates expected.

## 4. Track C — upload-only links

### Goal

A link that lets someone upload files into a folder without listing,
downloading, or overwriting anything. The owner sees the files in their
normal folder tree.

### Data model

Reuse the existing share row with `kind = "link"` and `permission = "write"`;
the current API rejects that combination, but the schema already allows it.
Add one migration:

```sql
ALTER TABLE shares ADD COLUMN max_files INTEGER;
ALTER TABLE shares ADD COLUMN max_bytes INTEGER;
ALTER TABLE shares ADD COLUMN uploaded_files INTEGER NOT NULL DEFAULT 0;
ALTER TABLE shares ADD COLUMN uploaded_bytes INTEGER NOT NULL DEFAULT 0;
```

`max_*` NULL means “use the server/link default”. The counters are updated in
the same transaction that commits an upload.

Do not add `kind = "drop"`: it would force a table rebuild and a second public
route family. “Link + write” is the drop mode.

### Creation

Extend `POST /api/shares` for links:

- `permission: "write"` creates an upload-only link.
- `max_files`, `max_bytes` optional; server defaults if omitted.
- expiry/password reuse the existing fields.
- Reject `write` on an encrypted folder: the server cannot encrypt public
  plaintext, and silently writing plaintext into an E2EE tree violates the
  boundary.
- Reject `write` on a file (only folders).
- Return `upload_only: true`, limits, and the `/s/<token>` URL.

`PATCH` for links: expiry/password only. Do not allow switching read ↔ write
after creation; revoke and recreate.

### Public upload flow

Public page `/s/<token>` reads meta and renders either a read-only view or an
upload form.

Add `PUT /public/{token}/upload?name=<filename>`:

- Auth: valid link token, not expired, link session cookie if password
  protected. Same lockout/rate-limit rules as `public_unlock`.
- Body: raw bytes, streamed. Reject missing/oversized `Content-Length` before
  reading; enforce the configured maximum.
- Target: the shared folder, resolved through `kolimi-vfs` as the owner.
  Reject if the folder is encrypted, trashed, or missing.
- Filename: sanitize `\`, `/`, NUL, control characters; cap length; strip
  leading dots? Do not allow traversal. Collision policy: suffix ` (2)`,
  ` (3)`; never overwrite.
- Counters: increment only after the file is committed; enforce `max_files` and
  `max_bytes` atomically. Owner quota still applies.
- Response: `201` with a generic “Uploaded” and the sanitized filename; no
  listing, no path disclosure beyond what the uploader supplied.
- Audit: `share.drop.upload` with share id, size, and outcome; do not log
  file contents.
- `GET /public/{token}/list` and `/download` return `403` for write links.

Upload page:

- Drop zone, file picker, per-file progress, remaining limits, expiry/password
  state.
- “Files go to the owner; you cannot see what is already there.”
- No filenames of existing files are revealed; collision suffixes are local
  to the upload.

### Abuse controls

- Default per-link limits: e.g. 20 files / 1 GiB; configurable.
- Per-link and per-IP rate limit; existing password lockout.
- Short default expiry for drop links (7 days recommended).
- Optional password; if omitted, warn that anyone with the URL can upload.
- No public listing/download; no overwrite; owner quota enforced.
- Consider a global `KOLIMI_PUBLIC_UPLOADS` kill switch; default on in 0.7.0
  only after abuse tests pass.

### UI

- Share dialog adds **Request files** mode; fields for expiry, password, max
  files, max bytes.
- Shared page shows “File request” with used/limit counters; revoke and copy.
- Owner sees uploads in the target folder; no separate inbox required in v1.
  A future “Requests/<share-id>” auto-folder can be added without changing the
  link model.

### Tests

- Upload succeeds into a plaintext folder; owner sees the file.
- Invalid/expired/revoked/password-protected link behavior.
- `GET list`/`download` rejected for write links.
- Max files, max bytes, owner quota, collision suffix.
- Path traversal and control characters in `name` rejected or sanitized.
- Encrypted/trashed/missing target rejected.
- Audit/rate-limit/lockout.
- Playwright: public upload page; Shared page counters; axe.

### Acceptance

A user can send a link that only accepts uploads, with a hard cap and expiry,
without exposing the folder contents or accepting plaintext into an encrypted
tree.

## 5. Cross-cutting security

- **E2EE boundary:** the server never receives plaintext file keys or names
  for encrypted content. Track A copies fragments only on the client; Track C
  refuses encrypted targets.
- **Deny by default** for scoped app passwords. A new route must be added to
  the matrix or it requires `*`.
- **No scope fallback:** a failed app-password scope check must not silently
  use a cookie session.
- **No secret logging:** app-password tokens, link passwords, link fragments,
  and decrypted filenames never enter logs/audit details.
- **Abuse:** upload links get per-link caps, rate limits, expiry, and owner
  quota. No listing, no overwrite.
- **Audit:** share create/revoke/update and drop upload are audited; public
  upload audit must not contain file content.

- **0.6.0:** Track A + B. No public upload surface. Migrations: app-password
  scopes.
- **0.7.0:** Track C. Migrations: share limits/counters. Security review of
  the public upload endpoint before tagging.
- Docs: update `usage.md` (Shared page), `reference.md` (scope fields, upload
  endpoint), `how-to.md` (file requests, scoped tokens), `clients.md`
  (app-password presets), `threat-model.md` (public upload surface).
- `CHANGELOG.md` and `ROADMAP.md` entries only when scheduled.

## 8. Open questions

1. Scope granularity: protocol-level (`files`, `caldav`, `carddav`, `sync`) is
   enough for v1, or do we need per-folder scopes? Recommendation: protocol
   only; per-folder is a larger authz change.
2. Default scope for new app passwords: “Sync client” or “Files read/write”?
   Recommendation: Sync client preset for desktop/mobile; Full access explicit.
3. Drop link inbox: upload directly into the chosen folder (recommended) or
   auto-create `Requests/<share-id>`? Direct is simpler; the owner already
   chose the folder.
4. Drop link default expiry: 7 days vs never. Recommendation: 7 days.
5. Encrypted folder drop links: reject in v1 (recommended) or design a
   client-side encrypted drop protocol later.
6. Shared page encrypted folder links: if the client cannot rebuild all
   required keys, show a clear “open the file to copy the link” state rather
   than a broken URL.
