# RFC 0007: Client-side end-to-end encryption (E2EE)

Status: draft (design) · Depends on: RFC 0001 (storage engine),
RFC 0002 (sync protocol), RFC 0006 (sync client)

## Summary

Optional per-user, per-file E2EE on top of the existing chunked CAS.
The client encrypts chunk bytes before chunking/uploading; the server
stores opaque blobs and never sees plaintext, file keys, or the master
key. The design preserves server-side versioning, delta sync, and
integrity checking by moving them onto ciphertext. It is honest about
what leaks: metadata (paths, sizes, timestamps, access patterns) and
equality of identical chunks within one file's history.

## Goals

- The operator (A5 in the threat model) cannot read file content.
- Works with the existing engine: server-side CAS dedup and GC,
  versions, trash, delta sync, integrity verification (RFC 0001).
- No silent data loss: keys are recoverable via a printed recovery
  code; losing every unlock path is a documented, explicit trade-off.
- Unlock with a passphrase, a passkey (WebAuthn PRF), or the recovery
  code.

## Non-goals (v1)

- Hiding metadata: names, sizes, mtimes, and access patterns remain
  visible to the server.
- Cross-file deduplication (each file has its own key) and server-side
  content search/previews for encrypted files (name/path search still
  works; the server marks hits as content-encrypted).
- Sharing encrypted files with other users, group keys, and forward
  secrecy (v2: wrap file keys to recipient public keys; MLS for groups).
- Encrypted WebDAV: encrypted nodes appear as opaque blobs to generic
  DAV clients; the Kolimi sync client decrypts locally.

## Key hierarchy

```
passphrase ──Argon2id──▶ KEK ┐
passkey PRF ──HKDF─────▶ KEK ┤─unwrap─▶ UMK (user master key, 32B random)
recovery code ──HKDF───▶ KEK ┘
                                │
              ┌─────────────────┴──────────────────┐
              ▼                                    ▼
        FK (file key, 32B random)          manifest key
        stored wrapped under UMK           (derived from FK)
```

- **UMK** is generated once per user at E2EE setup. The server stores
  only wrapped copies plus KDF parameters; it never sees UMK or KEK.
- **Unlock paths.** The passphrase path uses Argon2id (m=64 MiB, t=3,
  p=1, per-user salt). The passkey path uses the WebAuthn PRF extension
  output (32 bytes, stable per credential) fed through HKDF — the same
  ceremony that logs in also unwraps the key material, so passkey-only
  mode (below) composes naturally. The recovery code is 256 random bits
  shown once; it wraps a second copy of UMK.
- **File key (FK).** Every encrypted file gets a fresh random FK,
  stored wrapped under UMK in the node's metadata (server-side column,
  opaque to the server). Versions of a file share one FK.

## Chunk and manifest encryption

Chunking happens *after* encryption, so the server's CAS operates on
ciphertext:

- **Chunk AEAD.** XChaCha20-Poly1305 with key
  `HKDF(FK, "kolimi-chunk-v1")` and a deterministic nonce
  `HKDF(FK, "kolimi-nonce-v1" || BLAKE3(plaintext_chunk))[..24]`.
  Deterministic encryption means identical plaintext chunks produce
  identical ciphertext, so the server's chunk-level delta and CAS dedup
  keep working within a file's version history. Cross-file dedup is
  impossible (different FK). Trade-off: the server can tell that two
  chunks inside one file's history are equal — accepted and documented.
- **Chunk hashes / content id.** The manifest hashes ciphertext (the
  server's BLAKE3 check still catches corruption end-to-end); the file
  `content_id` is the hash of the ciphertext manifest, so the server
  cannot correlate content across users.
- **Manifest.** Encrypted with FK (random nonce) and stored where the
  plaintext manifest used to be; the server treats it as an opaque
  blob with a size cap.
- **AAD.** Binds the file key id and chunk index only. Paths are not
  bound (renames must not invalidate data).

## Server behavior

- Nodes carry an `encrypted` flag; the server never attempts to parse
  content, manifests, or previews for those nodes.
- Search indexes name/path only; content hits are omitted with an
  explicit "encrypted" marker.
- Sync, versions, trash, janitor GC, backup, and `verify` operate on
  ciphertext unchanged (RFC 0001 machinery is content-agnostic).
- The server can still enforce quotas and integrity; it cannot repair
  or scan encrypted payloads — by design.

## Client behavior (kolimi-sync)

- `--e2ee` unlock: passphrase prompt, passkey PRF (desktop/mobile
  shells), or recovery code. Keys are held in memory only; a small
  wrapped-UMK cache can be added later behind an OS keychain.
- Pull: decrypt manifests/chunks before writing local files.
- Push: encrypt, then run the unchanged RFC 0002 push path.
- Conflict policy (RFC 0006) is unchanged: it operates on plaintext
  locally and ciphertext remotely.

## Migration and scope

- Opt-in per directory. Existing plaintext nodes stay plaintext;
  encrypting a directory marks its nodes and rewrites content once.
- Mixing is allowed inside a tree (a plaintext file in an encrypted
  directory is a client-side policy error, rejected by the client).

## Recovery

The recovery code is generated at setup and must be acknowledged
before E2EE is enabled. Rotating the passphrase rewraps KEK; rotating
the recovery code issues a new wrapping and invalidates the old one.
Losing all unlock paths means the data is unrecoverable — the client
makes this explicit at setup.

## Crypto primitives

| Purpose | Primitive | Crate |
| --- | --- | --- |
| AEAD (chunks, manifests, key wraps) | XChaCha20-Poly1305 | `chacha20poly1305` |
| Key derivation | HKDF-SHA256 | `hkdf`, `sha2` |
| Passphrase KDF | Argon2id | `argon2` (already used) |
| Hashing / content ids | BLAKE3 | `blake3` |
| Randomness | OS CSPRNG | `getrandom` via `rand` |

## Testing and interop

- Deterministic chunk-encryption test vectors committed to the repo;
  any client implementation must reproduce them bit-for-bit.
- Round-trip tests through a live server: plaintext → encrypt → push →
  pull → decrypt equals the original, including versions and delta
  edits.
- Negative test: after an encrypted push, no stored chunk or manifest
  contains a plaintext marker (guards against accidental plaintext
  fallback).
- Two independent implementations (the sync lib and a minimal test
  harness) must decrypt each other's uploads — the M6 "E2EE interop
  tests" exit criterion.

## Open questions

1. PRF support matrix across browsers/platforms; fallback UX when a
   passkey lacks PRF.
2. Whether to encrypt thumbnails/previews client-side (v2 candidate).
3. Public links to encrypted files: key-in-fragment (`#k=…`) keeps the
   server blind but leaks the key to anyone with the URL — same trust
   model as the link itself; decide in v2.
4. Per-directory keys to reduce metadata correlation vs per-file keys
   (current choice).
