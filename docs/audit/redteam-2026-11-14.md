# Internal red-team report — 2026-11-14

**Status:** internal pass complete; fixes applied in the working tree, not yet
committed. **This is not an external audit.** The external crypto review in
[`README.md`](README.md) and [`mls-delta.md`](mls-delta.md) remains pending.

**Scope:** Kolimi server, HTTP/WebDAV/CalDAV/CardDAV surface, the web→host
boundary, E2EE v1/v2 (RFC 0007), MLS groups (RFC 0012), enrollment (RFC 0008),
and the deployment/packaging paths that affect them.

**Base:** commit `ae470bf` (workspace 0.4.5) plus the fixes listed below.
**Method:** white-box review plus black-box testing against an isolated
loopback instance (`KOLIMI_DATA=/tmp/kolimi-redteam`, debug build), with two
to three test accounts. No production data or external systems were touched.

## Executive summary

The baseline is stronger than average for a young self-hosted server: path
handling, CSRF, session binding, public-link scoping, the image sandbox, and
the MLS epoch CAS all held up. The material issues were at the boundaries
that are easy to miss: active content served from the app origin, security
flags writable by share recipients, and MLS resource scoping.

Two high-impact issues were found and fixed: stored XSS through shared
HTML/SVG (admin-session takeover), and a cross-client encryption gap where
CLI-created encrypted roots were not marked server-side, so the web UI
uploaded plaintext into them. Nine medium issues were fixed (E2EE folder
downgrade, MLS keyring clobbering, key-package consume IDOR,
commit-via-message path, identity rotation, TOTP re-enrollment, passkey
retention through account recovery, the encrypted commit guard, and
session-only keyring replacement), plus the follow-up pass below. Nine
low issues were fixed, including passkey re-authentication, PRF argv
exposure, and the post-unlock mount-name refresh.
One local-only dependency CVE is accepted and documented. One suspected
file-key issue was investigated and rejected as a false positive after a
legitimate write-recipient flow failed under the proposed restriction; the
existing re-wrap behavior is intentional.

### RT-01 — High — Stored XSS through shared HTML/SVG

**Where:** `crates/kolimi-webdav/src/lib.rs` (`get`), public download in
`crates/kolimi-server/src/api_shares.rs`.

**Issue:** WebDAV `GET` served user-uploaded `.html`/`.svg` with the real MIME
type, no `Content-Disposition`, and no sandbox CSP. A user could share an
active file with another user (normal product behavior); opening the
`/dav/...` path executed script in the Kolimi origin with the victim's
session. The CSRF cookie is intentionally script-readable, so the script
could drive every API. An admin victim meant persistent admin creation and
access to all non-E2EE data.

**Evidence:** Chromium with mallory's real session loaded the shared file and
the payload read her authenticated identity:

```
status: 200
title: XSS:{"is_admin":false,"username":"mallory"}
```

**Fix:** every DAV `GET`/`HEAD` file response now carries
`Content-Security-Policy: sandbox; default-src 'none'`. Active types
(`text/html`, `application/xhtml+xml`, `image/svg+xml`, XML/`+xml`) also get
`Content-Disposition: attachment`. Public downloads already forced
attachment and now carry the same CSP. Regression test:
`active_content_is_served_as_inert_attachment`.

**Re-test:** the same Chromium flow now starts a download (`xss.html`), never
renders a document, and the title stays empty. Full WebDAV suite: 49/49;
litmus: 104/104.

**Longer-term recommendation:** serve user content from a separate origin.

### RT-02 — Medium — Write recipient could disable folder encryption

**Where:** `crates/kolimi-server/src/api_browse.rs` (`set_encryption`).

**Issue:** the handler required write permission but not ownership. A
write-share recipient could call `POST /api/files/encrypt` on the shared
folder and flip the owner's `encrypted` flag to `false`. Clients read that
flag to decide whether uploads must be encrypted, so this was a plaintext
downgrade: the owner's next uploads would be readable by the server
(honest-but-curious operator) and by anyone with access.

**Evidence:** as mallory (write share of alice's `/Downgrade`):

```
POST /api/files/encrypt {"path":"/Shared with me/Downgrade","encrypted":false}
→ 200 {"encrypted":false,...}
alice's /api/files/info?path=/Downgrade → encrypted:false
```

**Fix:** owner-only check (`access.owner_id == user.user_id`) before the
subtree uniformity scan. Regression test:
`write_recipient_cannot_change_folder_encryption`.

**Re-test:** mallory now gets `403 only the owner can change folder
encryption`; alice can restore the flag.

### RT-03 — Medium — MLS keyring accepted without a revision

**Where:** `crates/kolimi-server/src/api_mls.rs` (`KeyringQuery`,
`put_keyring`), `crates/kolimi-db/src/mls.rs` (`set_mls_keyring`).

**Issue:** `if_revision` was optional, and the `None` branch performed an
unconditional upsert. Any writer could overwrite the current epoch's
encrypted keyring without losing an optimistic-concurrency race, defeating
the documented "a concurrent writer loses instead of overwriting newer
keys" invariant. Impact is integrity/availability: group members can be
locked out of new file keys.

**Fix:** `if_revision` is now required. `0` means "no keyring yet"; a stale
revision returns `409`; omission is a hard `400`. The legacy branch was
removed. Clients already sent the revision.

**Re-test:** no revision `400`, revision 0 `204`, stale 0 `409`, revision 1
`204`. Test: `keyring_writes_require_a_matching_revision`.

### RT-04 — Medium — Key-package consume IDOR/DoS

**Where:** `crates/kolimi-server/src/api_mls.rs` (`consume_key_packages`),
`crates/kolimi-db/src/mls.rs`.

**Issue:** the endpoint accepted raw sequential IDs with no caller, group, or
ownership check. Any authenticated user could enumerate packages via
`GET /api/mls/key-packages/{username}` and burn every account's enrollment
pool, preventing new devices from joining groups.

**Evidence:** alice consumed mallory's package `id=1` (`204`); mallory's pool
was empty afterwards.

**Fix:** the request now carries the group `path`. The caller needs write
access to that group. Each package ID is resolved to its owner; a caller may
consume its own packages, or packages of users who already have access to
that node (checked by a recursive ancestor/share query, not the caller's
mounted path). Consumption is audited. Sync and web UI send the path.

**Re-test:** consume for `/Vault` (mallory has no access) `403`; for
`/Downgrade` (write share) `204`; pool is consumed only in the allowed case.
Tests: `key_package_consumption_is_scoped_to_the_group`.

### RT-05 — Medium — Commits/Welcomes through the message endpoint

**Where:** `crates/kolimi-server/src/api_mls.rs` (`post_message`).

**Issue:** `/api/mls/messages` accepted `kind: "commit"` and `"welcome"` and
advanced the epoch, bypassing the atomic commit+Welcome endpoint. A commit
that adds a device could be published without its Welcome, breaking the
documented atomicity invariant; the two-row transaction could be split.

**Fix:** the message endpoint now rejects `commit`/`welcome` with a pointer to
`POST /api/mls/commit`. Clients only used that route as a fallback for old
servers, which keep accepting it. Proposals and application messages still
work. Tests updated (`commits_and_welcomes_must_use_the_atomic_endpoint`).

### RT-06 — Medium — Session-only E2EE identity rotation

**Where:** `crates/kolimi-server/src/api_e2ee.rs` (`put_identity`),
`crates/kolimi-db/src/e2ee.rs` (`set_identity`).

**Issue:** a session (no master key required) could overwrite the account's
X25519 identity. Future file keys would then be wrapped to a key the session
attacker controls, converting a session compromise into decryption of future
shares — contrary to the threat-model claim that session theft leaks no
E2EE content.

**Evidence:** PUT with a fresh valid public key returned `204`; GET returned
the attacker's key.

**Fix:** identity is create-once. An identical retry is accepted; a different
key returns `409 identity is already set; rotation requires recovery`.
Normal first-use flows only publish when the identity is absent, so they are
unaffected. Test: `identity_is_create_once`; invariant added to
`crypto-review.md`.

**Remaining gap:** a session attacker who reaches an account **before** E2EE
setup can still squat the identity. A recovery-based rotation/reset flow is
future work.

### RT-07 — Low/Medium — Metrics cardinality DoS

**Where:** `crates/kolimi-server/src/metrics.rs` (`record`).

**Issue:** unmatched routes used the raw request path as a Prometheus label.
An unauthenticated client could create unbounded metric series by requesting
random URLs. 10,000 unique 404 paths produced ~150,000 series and ~5 MB RSS;
sustained traffic also explodes any scraping Prometheus.

**Fix:** only `MatchedPath` is labeled; unmatched requests share
`path="unmatched"`. Test: `unmatched_paths_share_one_metric_label`.

### RT-08 — Low — Backup followed symlinks

**Where:** `crates/kolimi-store/src/lib.rs` (`copy_tree`).

**Issue:** every non-directory entry, including symlinks, was passed to
`fs::copy`, which follows the link. A local attacker who could write into the
blob tree could pull unrelated readable host files into a backup. Packaged
data dirs are `0700`, so this is local-only, but backups are often shipped
elsewhere.

**Fix:** only regular files are copied; symlinks and special files are
skipped. Test: `copy_tree_skips_symlinks`.

### RT-09 — Low — `--data` ignored by management subcommands

**Where:** `crates/kolimi-server/src/main.rs`.

**Issue:** `user`, `group`, and `audit` re-read only `KOLIMI_DATA` and
defaulted to `./kolimi-data`, while `serve --data` honored the flag. An
operator could run `kolimi-server --data /var/lib/kolimi user recover ...`
and silently modify a different database — particularly dangerous during
incident response (password resets, disables). The top-level help made
`--data` look global.

**Fix:** `data` is a real global arg used by every subcommand; `serve`,
`backup`, `verify`, `audit`, `user`, and `group` all consume it. The
`Backup`/`Verify` duplicate flags were removed. Docs updated. Unit test:
`data_flag_is_global` (before and after the subcommand name).

**Re-test:** `--data /tmp/cli-check user add ...` writes only there; no stray
`./kolimi-data`; `user list --data /tmp/cli-check` works.

### RT-10 — Low — Error and existence leaks

**Where:** `crates/kolimi-server/src/api_shares.rs`,
`crates/kolimi-server/src/api_sync.rs`.

**Issue:**
- Revoking a share you do not own returned `403` ("not allowed to revoke this
  share"), distinguishing existing share IDs from missing ones (`404`).
- A missing manifest returned `storage error: blob <hash> not found`, exposing
  internal error text.
- `chunks/exist` on a read-only shared path returned `500` because the error
  mapping collapsed all stat errors.

**Fix:** share revoke returns `404`; manifest 404/500 bodies are generic
(`{"error":"not found"}` / `internal server error`) while 400/409 remain
actionable; `chunk_owner` maps not-found/forbidden/parent errors explicitly.
Tests updated/added (`sharing.rs`, `sync.rs`).

### RT-11 — Low — MLS device roster enumeration

**Where:** `crates/kolimi-server/src/api_mls.rs` (`get_user_devices`).

**Issue:** any authenticated user could read any account's MLS roster
(device IDs, operator-visible names, public signature keys), despite the
docs describing the endpoint as share-owner-only.

**Fix:** the caller must be the account itself or have a mutual user/group
share relationship (new `users_share_access` query). Key packages remain
public to authenticated users because they are needed before a share exists.

**Re-test:** mallory (has shares with alice) `200`; carol (no relationship)
`404`. Negative case added to the roster test.

### RT-12 — Low — MLS revocation poisoning

**Where:** `crates/kolimi-server/src/api_mls.rs` (`post_revocation`,
`delete_revocation`).

**Issue:** any writer could add or clear a revocation for an arbitrary
signature key. A co-writer could suppress a victim device's automatic
re-add, or clear a deliberate removal so a stale key package can reintroduce
the device. The list is client-asserted by design, but the writer scope was
too broad.

**Fix:**
- Owner: may record or clear any revocation in the group.
- Non-owner writer: may only self-revoke a device in its own roster, and only
  while no other account claims the same signature.
- Clearing is owner-only.

**Re-test (mallory, write share of `/Vault`):** arbitrary key `403`, own
roster key `204`, non-owner clear `403`, owner clear `204`, owner arbitrary
`204`. Tests: `revocations_are_owner_or_self_only`.

### RT-13 — Medium (accepted) — `libsqlite3-sys` CVE-2026-119375

**Where:** `libsqlite3-sys 0.37.0` via `sqlx 0.9.0`.

**Issue:** bundled SQLite < 3.54.0 can return uninitialized page-cache memory
when opening a database plus a crafted sibling `-wal` with a mismatched page
size. Local vector; requires opening attacker-written files. `cargo audit`
and `cargo deny` failed on it, contradicting the previous claim that deny
stayed green.

**Why accepted:** `sqlx 0.9.0` (latest) pins `libsqlite3-sys 0.37`; the fixed
0.39 arrives with a future `rusqlite`/`sqlx` release. Packaged deployments
run with a `0700` data dir (`UMask=0077`, deb/installer `chmod 700`), so a
remote user cannot plant the pair. The plausible path is restoring an
untrusted backup. Documented with a revisit condition in
`docs/known-advisories.md`, `.cargo/audit.toml`, and `deny.toml`.

`rustix 1.1.5` (RUSTSEC-2026-0486) was upgraded to 1.1.6 and is no longer
flagged.

### RT-14 — Info — Deployment and supply-chain backlog

- Raw-binary runs create `0755` dirs / `0644` DB under the default umask;
  packages correctly use `0700`/`UMask=0077`. Consider enforcing `0700` in
  `AppState::init`.
- No HTTP header/read timeout; slowloris is possible without a reverse proxy.
- `KOLIMI_USER_QUOTA_BYTES=0` means an authenticated user can fill the disk by
  default; set a quota.
- Previews fail closed on non-x86_64 (empty seccomp allowlist) — broken
  feature, not a security hole.
- CLI user deletion while the server runs leaves search-index documents until
  the next restart (logged warning); the in-process API path cleans them.
- GitHub Actions are pinned to tags, not commit SHAs; `install.sh` checksums
  come from the same origin unless cosign is already installed. No
  `SECURITY.md`.

### RT-15 — High — CLI encrypted roots were invisible to the web UI

**Where:** `crates/kolimi-sync/src/lib.rs` (`E2eeOptions`,
`EncryptPolicy`), browser upload decision in
`crates/kolimi-ui/src/browser/uploads.rs`.

**Issue:** `--e2ee-root Private` encrypted files and names client-side but
never called `POST /api/files/encrypt`. The server therefore reported the
folder as plaintext, and the browser (which uses the server flag to decide
whether to encrypt) uploaded **plaintext** into a folder the CLI considered
E2EE. The server operator could read it, and the two clients disagreed about
the folder's state.

**Evidence:** a persistent CLI fixture with `--e2ee-root Private` returned:

```
/api/files/info?path=/Private → {"encrypted":false,...}
/api/browse?path=/Private     → encrypted:false, children encrypted:false
```

A browser upload into that folder produced a `Download` link and no
“Encrypted” marker (plaintext DAV object) instead of “Download & decrypt”.
After the fix, the same upload produced a 201 chunk + 200 commit, the tree
entry was `encrypted:true`, and a scan of every stored chunk did not contain
the plaintext marker.

**Fix:** after each push, the sync client publishes every configured
encrypted root with `POST /api/files/encrypt` (idempotent, owner-only). A
received share is skipped (the owner controls its flag), a not-yet-created
folder is retried next pass, and a folder that still contains plaintext
fails the sync with a clear error instead of silently continuing. Desktop
uses the same sync library.

**Tests:** the `mls_sync` fixture now asserts `/Private` is flagged after
the first sync; the new browser test asserts the server flag, ciphertext
chunks, DAV refusal, and browser decryption.

### RT-16 — Medium — TOTP re-enrollment from a session

**Where:** `crates/kolimi-server/src/api_2fa.rs` (`enable`).

**Issue:** `POST /api/totp/enable` verified only the new secret's code and
replaced any existing TOTP secret and recovery codes. A stolen session
(without the current second factor) could enroll its own authenticator,
permanently locking the real user out until an administrator recovery.

**Fix:** when TOTP is already enabled, `enable` returns
`409 TOTP is already enabled; disable it first`. Disabling already requires a
current TOTP or recovery code. Test:
`totp_cannot_be_re_enrolled_from_a_session`.

### RT-17 — Medium — Recovery kept attacker-added passkeys

**Where:** `crates/kolimi-server/src/main.rs` (`user recover`),
`kolimi-server/src/admin.rs`.

**Issue:** `user recover` reset the password, dropped sessions, and cleared
TOTP, but kept every passkey unless `--remove-passkeys` was passed. A
passkey added during a session compromise survived the recovery, leaving the
attacker with a working login.

**Fix:** recovery now removes passkeys by default; `--keep-passkeys` is an
explicit opt-in for known-safe devices. Docs and help updated. Test:
`cli_recover_removes_passkeys_by_default`.

### RT-18 — Low — Passkey changes had no re-authentication

**Where:** `crates/kolimi-server/src/api_passkey.rs`
(`register_finish`, `delete`).

**Issue:** an authenticated session could add a passkey without proving the
password or a current second factor. Passkey login starts a session directly
(a passkey is its own strong factor), so a session attacker could add a
credential that survives password changes and bypasses TOTP. Removing a
passkey was equally ungated, allowing an attacker to erase the owner's only
strong factor.

**Fix:** `POST /api/reauth` verifies the account password or a current
TOTP/recovery code and returns a single-use five-minute token. Passkey
registration completion and deletion require that token; failed attempts
are lockout-tracked and audited. Passkey-only accounts (no password) can
mint the same token with a fresh assertion through
`POST /api/reauth/passkey/begin|finish`. Removing the last passkey on a
passwordless account is refused to prevent self-lockout. The browser
prompts for confirmation instead of silently changing credentials. Tests:
`passkey_changes_require_reauthentication`,
`passkey_only_account_cannot_remove_its_last_passkey`,
`passkey_full_register_and_login_flow`, the scoping test, and the browser
virtual-authenticator scenario.

### RT-19 — Medium — Encrypted-folder guard rejected edits without a re-wrap

**Where:** `crates/kolimi-vfs/src/vfs.rs` (`commit_manifest`).

**Issue:** once a folder was marked encrypted, the commit guard required a
`wrapped_key` on **every** manifest commit. Clients only send the wrap when
they create a key; ordinary edits reuse the key already stored on the node.
After RT-15 started marking folders, CLI edits began failing with `409`
(this was caught by the MLS sync suite, not by the browser test).

**Fix:** the guard now requires a key only when the node does not already
have one (`path_is_encrypted && wrapped_key.is_none() && !was_encrypted`).
New files and plaintext nodes under an encrypted root still require a wrap;
existing encrypted nodes may reuse their stored key. Tests: full
`mls_sync` (9/9), WebDAV (50/50), E2EE (5/5), share (3/3), sync (9/9).

### RT-20 — Medium — A session could replace or roll back the account keyring

**Where:** `crates/kolimi-server/src/api_e2ee.rs` (`put_keyring`),
`crates/kolimi-db/src/e2ee.rs`, `crates/kolimi-sync/src/lib.rs`
(`upload_keyring`).

**Issue:** `PUT /api/e2ee/keyring` accepted any session, so a stolen cookie
could replace the wrapped keyring with an attacker-controlled one (unlock
denial of service) or replay an older blob after a passphrase rotation.
The client already refused an older epoch, but the server did not.

**Fix:** the server now stores the keyring epoch and rejects a lower one;
`PUT` requires the caller's current `if_epoch` (optimistic concurrency) and,
when a keyring already exists, a fresh re-authentication token. The sync
client exchanges its configured password for a token before replacement and
sends the epoch it read; the browser asks for the account password when
changing the encryption passphrase. The first setup still works without a
token because there is nothing to overwrite. Tests:
`keyring_replacement_requires_reauth_and_rejects_rollback` plus the full
E2EE/sync suites.

**Residual:** the encrypted blob is still opaque to the server, so a
compromised master key or an authorized client can write a valid keyring;
the control protects the credential-management path, not key custody.

### RT-21 — Low — PRF secret visible in the process list

**Issue:** a 64-hex-character CLI argument is visible to other local users

### Addendum — browser E2EE and PRF verification

The browser suite now covers eight scenarios (`browser-e2e/tests/web.spec.ts`,
8/8 passing):

- E2EE unlock, upload into an encrypted folder, ciphertext-at-rest check
  over every chunk, server refusal on `/dav`, and browser-side decryption.
- A recipient (legacy folder share) unlocks, sees the decoded mount name,
  and decrypts the shared file.
- Adding a passkey shows the password confirmation first, then completes
  through a virtual authenticator; the credential appears in the panel.
- The existing migration and MLS-reset flow still passes.

PRF review: the server stores the PRF wrap opaquely in the keyring; wrong or
short PRF outputs fail closed (`kolimi-crypto` test added for a real PRF
wrap). The PRF secret can be passed through `KOLIMI_E2EE_PRF` or
`--e2ee-prf-stdin`, avoiding argv exposure; `--e2ee-prf` remains available
for compatibility.
No server-side PRF finding.

### FP-01 — Not a bug — Per-node wrapped-key overwrite

`PUT /api/files/key` and the `wrapped_key` field in a manifest replace the
stored blob. This was initially treated as a data-loss vector and blocked,
but the `mls_sync` write-recipient test showed the design: for shared/MLS
files the node key is an opaque "this file is encrypted" marker, re-wrapped
under the editor's master on every edit, while decryption uses the epoch
keyring. The restriction was reverted and the behavior pinned by
`file_keys_are_rewrapped_on_edit`.

## What held up

- **WebDAV compliance:** litmus 104/104 (basic 16, copymove 13, props 30,
  http 4, locks 41), before and after the fixes.
- **Auth:** per-account+IP lockout, X-Forwarded-For ignored unless
  `KOLIMI_TRUST_PROXY` is set, generic login errors, dummy Argon2 timing,
  random per-login sessions, hashed session tokens, scoped logout, CSRF
  double-submit bound to the session, `SameSite=Strict` + `HttpOnly`,
  credential-version invalidation on password change.
- **Authorization:** per-user namespaces, share mount permissions, owner-only
  share management, admin gating, manifest/chunk/preview IDOR checks.
- **Traversal:** `/dav`, public links, and preview reject `..`, encoded
  variants, control characters, NUL, overlong segments, and depth bombs.
- **Public links:** 128-bit tokens, path scoping, password flow, forced
  attachment downloads.
- **Preview:** separate worker with rlimits, `no_new_privs`, Landlock,
  seccomp, 16K dimension cap, 256 MB decoder cap, 10 s timeout, 4 concurrent
  workers, fail-closed if the sandbox is incomplete.
- **E2EE guards:** encrypted nodes are refused by WebDAV, preview, and
  search; per-user blob namespaces prevent cross-user chunk/manifest access;
  owner-only file keys; share-key rows are addressed to one recipient.
- **MLS server rules:** monotonic epochs, exactly-one CAS winner for
  concurrent commits, atomic commit+Welcome, keyring revision CAS, message
  and keyring size caps, pagination capped at 1000 messages.
- **Enrollment:** cross-user GET/approve/delete `404`; expired approval
  `400`; concurrent approvals first-wins (`204`/`400`); cross-user device
  delete `404`; device code mismatch detected client-side.
- **Systemd unit:** strong hardening (`ProtectSystem=strict`, empty
  capability set, `UMask=0077`), loopback default bind.

## Remaining risks and recommendations

1. **Keep the full CI matrix green** after the follow-up commits (test,
   supply-chain, browser, litmus, fuzz, and desktop jobs).
2. **Account keyring integrity:** replacement now needs a re-auth token and
   an exact epoch, and rollback is rejected. Residual: an authorized client
   or a compromised master key can still write a valid keyring; the server
   cannot judge key custody.
3. **Passkey credential management:** registration completion and deletion
   now require a single-use re-auth token (RT-18). Passkey-PRF itself fails
   closed on a wrong secret; platform shells should use the stdin/environment
   path rather than argv.
4. **External audit:** the v1/v2 E2EE package and MLS delta are still
   awaiting external review; this report does not change that.
5. **Deployment backlog:** enforce `0700` in the binary, add a header/read
   timeout, set a default quota, pin CI actions by SHA, and add
   `SECURITY.md`.

## Reproduction notes

```sh
KOLIMI_DATA=/tmp/kolimi-redteam ./target/debug/kolimi-server user add alice --password ...
KOLIMI_DATA=/tmp/kolimi-redteam ./target/debug/kolimi-server serve --bind 127.0.0.1:8080
```

`KOLIMI_DATA` (or the now-global `--data`) selects the instance. WebDAV
checks used Basic auth; API checks used a session cookie plus
`X-CSRF-Token`. Litmus is reproducible with `./scripts/litmus.sh`. Browser
proofs use `npm --prefix browser-e2e test`, which starts the deterministic
fixture in `scripts/browser-e2e-server.sh` and the system Chromium.
